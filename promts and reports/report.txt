4. EMERGENCY / SOS AUDIT
================================================================================

THE IMPLEMENTATION IS CORRECTLY EVENT-BASED, NOT GLOBAL/STATIC.

Each emergency is its own MongoDB document with its own callStatus,
escalationCycle, escalationPriority, and timeline
(backend/app/services/emergency_service.py:119-141). There are NO hasCalled
flags, NO module-level mutable call state, NO cooldowns. State transitions are
validated by a real state machine (backend/app/emergency/state_machine.py:21).
Manual SOS, confirmation, cancellation, no-response, acknowledgment and
escalation are all implemented and persisted.

WHY THE CALL WORKS ONLY ONCE -- STATUS: BROKEN, CONFIDENCE: HIGH
The cause is NOT global state; it is a lifecycle leak:

  1. _OPEN_STATUSES (emergency_service.py:24) counts everything except
     CANCELLED/RESOLVED as open -- including CONFIRMED, ACKNOWLEDGED,
     RESPONDING.

  2. route_reading (emergency_service.py:88-90) returns the existing emergency
     and refuses to create a new one whenever any open emergency exists.

  3. POST /emergencies/{id}/resolve exists (backend/app/api/emergencies.py:96)
     but HAS ZERO CALLERS in frontend/lib/. A grep for /resolve and resolve'
     across the whole Flutter tree found none. Nothing auto-resolves either:
     sweep_time_based_transitions (emergency_service.py:165) only escalates,
     never closes.

Once one emergency reaches CONFIRMED, that patient can NEVER trigger another AI
emergency -- permanently, across restarts, because it is persisted.

INCONSISTENCY
Manual SOS uses create() (emergency_service.py:42), which has NO dedup check, so
manual SOS spawns unlimited overlapping open emergencies -- the opposite
failure.

No hard-coded user IDs, no hard-coded phone numbers (only E.164 format hints in
validators), no demo accounts, no fake patients, no auth bypasses.

patientId always comes from the live session:
  frontend/lib/core/session.dart:26   userId => user?['id']
  restored from FlutterSecureStorage on boot (session.dart:60)
  -- NO missing-user-ID-after-restore issue.

Contacts are scoped by patientId on every read/write with ownership checks
(backend/app/api/contacts.py:21, :44, :58), and role authorization is enforced
via assert_owner_or_roles (backend/app/api/health.py:17).

UNCOMMITTED CHANGE IN auth_service.py -- CORRECT FIX
It replaces a check-then-insert TOCTOU race on refresh-token revocation with an
atomic unique-_id insert catching DuplicateKeyError. Import is present
(backend/app/services/auth_service.py:5) and the removed _is_jti_revoked has no
remaining references -- not broken.

FCM -- STATUS: PARTIAL
Code is real (backend/app/integrations/notification_provider.py:47), but
FCM_SERVICE_ACCOUNT_JSON= is empty in .env, so get_notification_provider returns
DemoNotificationProvider -> DEMO_RECORDED. Implemented and connected, NOT
CURRENTLY EXECUTING.
